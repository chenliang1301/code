# 基于姿态的网球正反手挥拍计数详细设计

设计日期：2026-11-08。状态：已开始实现规则/模板基线，板端与真实动作精度待验证。

实现入口及实际支持范围见[使用说明](TENNIS_SWING_USAGE_ZH.md)。下文保留完整目标设计；其中自适应阈值、完整特征组等尚未全部实现，以使用说明中的实现状态为准。

本文落实[总体技术方案](TENNIS_STROKE_ANALYSIS_PLAN_ZH.md)中的推荐方向，仅设计“姿态挥拍计数”。不增加网球检测、球拍检测或三维姿态模型。文中的接口、文件、命令行参数和测试项均为拟议设计，不能直接作为现有功能使用。

## 1. 设计结论与首版边界

首版复用 YOLOv8n-pose RKNN 的 17 点姿态，CPU 完成单人关联、质量判断、短时序特征、挥拍检测和正反手分类，完成一次动作后更新计数，并把数字绘制到现有 MJPEG 预览画面。

明确采用固定机位、单人 ROI、人工指定持拍手、少量示范校准的受控训练场景。统计的是正反手底线挥拍动作；有球练习和空挥均可计入，不能把这些数字标为真实击球次数。发球、截击、高压球不纳入正反手目标类。

二维姿态不能保证适用于任意视角。首选使肩肘腕清晰可见、身体横向运动未严重压缩的正面或背面斜视训练机位。机位是否可用必须通过校准数据检查；纯侧视、腕点长期遮挡和远距离小人体场景拒绝启动分类。正常随挥中短暂侧身可容忍，但不能要求接触瞬间肩线始终清晰。

本方案选择“时序规则检测动作 + 少样本模板比较正反手”作为首个可验证基线。模板无法区分类别时保留 UNKNOWN，不能无限修改规则强行输出。若测试不通过，再比较经过独立数据验证的轻量时序模型。

## 2. 功能与状态定义

### 2.1 计数口径

| 名称 | 语义 |
|---|---|
| FH | 已确认的正手底线挥拍事件数。 |
| BH | 已确认的反手底线挥拍事件数。 |
| UNKNOWN | 完整挥拍检测通过，但不能可靠区分正反手的事件数。 |
| REJECTED | 被排除的候选数，仅用于诊断，不属于已确认挥拍总数。 |
| TOTAL | `FH + BH + UNKNOWN`。 |

首版不设置 OTHER 计数：没有其他动作分类器时，不能假设能可靠识别所有发球和截击。已命中排除条件的候选进入 REJECTED；无法排除且类似挥拍的误触发应如实纳入测试误差。后续有独立验证的其他类别模型后再扩展 OTHER，不与当前统计混用。

挥拍次数在动作完成后更新，不实时猜测接触瞬间。每个事件绑定 `session_id + event_id`，提交操作幂等。页面刷新、重复绘制、多浏览器连接均不改变计数。

### 2.2 会话与运行状态

会话状态：`DISABLED / WAIT_ROI / WAIT_TARGET / CALIBRATING / RUNNING / PAUSED / ERROR`。

动作状态：`LOST / READY / PREPARE / SWING / RECOVER`。会话状态不是 RUNNING 时不得提交动作。质量下降首先暂停动作推进，而不是清空历史总数。

不启用网球模式时，现有普通姿态预览保持可用。静态图片只能显示姿态，不能进行时序计数；网球模式收到单图输入应明确提示不支持。

## 3. 当前实现约束与接入顺序

现有 `cpp/postprocess.h` 定义 `keypoints[17][3]` 为 `x,y,conf`，第三维绝不能当成深度。`cpp/main.cc` 负责相机帧逆时针旋转 90°、RKNN 推理、ROI 处理、骨架绘制、状态和时间绘制、JPEG 编码及发布。

现有 `MjpegServer::get_roi()` 只返回顶点，没有 ROI 修订号。新增分析应对规范化后的顶点内容做比较，仅在数值实际变化时触发重置动作历史，不能每帧调用都当成 ROI 变更。

建议帧处理顺序：

1. 从相机取得帧，立即记录主机单调时钟时间。
2. 统一处理画面旋转；使用同一坐标系推理、ROI 选择、校准和显示。
3. RKNN 推理得到人体检测及关键点，转换为无 RKNN 依赖的输入结构。
4. 读取 ROI，处理控制命令和配置变化，关联分析目标。
5. 更新姿态质量、短时缓存和状态机，最多提交一个新动作事件。
6. 按原流程绘制骨架、恢复 ROI 外画面、绘制 ROI 边框。
7. 绘制计数 HUD，避免与已有左上角状态及时间文字重叠。
8. JPEG 编码并调用 `preview_server.publish()`。

HUD 必须在 ROI 外原图恢复之后绘制。保留原始未标注帧供推理使用，不对已经绘制文字的图像重复推理。

## 5. 数据结构与接口约定

以下为接口草案，避免现有 RKNN 结构进入分析核心：

```cpp
struct Keypoint2D { float x, y, score; bool valid; };
struct PoseObservation {
    Keypoint2D points[17];
    float left, top, right, bottom, detection_score;
};
struct PoseFrame {
    uint64_t sequence;
    int64_t timestamp_us;
    int width, height;
    std::vector<PoseObservation> people;
};
struct SwingEvent {
    uint64_t event_id, target_generation, config_revision;
    int64_t start_us, peak_us, end_us;
    StrokeLabel label;
    float quality_score, template_distance, class_margin;
    RejectReason reason;
};
struct CounterSnapshot {
    uint64_t fh, bh, unknown, rejected;
    SessionState session_state;
    MotionState motion_state;
    uint64_t last_event_id;
};
```

`TennisAnalyzer` 拟提供 `update(frame)`、`apply_command(command)`、`snapshot()` 和 `drain_events()`。会话 ID 放在会话头及日志中；事件结构中的 event_id 仅在该会话内唯一。所有字段初始化，不能以 NaN 表达未分类分数；缺失用显式标志。拒绝原因采用稳定枚举并映射为可读文字。

输入约束：坐标、分数和人体框有限；框有正面积；时间戳严格递增；数组索引不作为目标 ID。超过配置人数上限先按 ROI 过滤，不静默丢掉当前目标。

## 6. 时间、坐标与输入方向

单调时钟用于动作时间，系统日期只用于展示和文件命名。摄像头首版采用取帧完成时间近似采集时间；若驱动存在缓存，其偏差必须在性能测试中记录，不能宣称精确曝光时间。文件回放使用源时间戳，离线关键点回放使用日志保存时间，不能用回放执行速度。

方向配置拟为 `rotation=0/90/180/270`，旧相机路径默认行为保持为逆时针 90°，网球用户需要确认最终人体直立。首版不增加分析前镜像；预览若仅用 CSS 镜像，分析及 ROI 坐标仍需明确映射，不能混用。

COCO 索引：左肩 5、右肩 6、左肘 7、右肘 8、左腕 9、右腕 10、左髋 11、右髋 12。左右均为人体解剖学左右，不能用画面位置交换。规范化画面点为 `(x/width,y/height)` 仅用于 ROI，计算动作特征仍从一致的像素坐标开始，避免非正方形画面改变角度。

## 7. 单人 ROI 和身份关联

ROI 未应用或顶点不足 3 个时进入 WAIT_ROI。ROI 中同时出现多名候选时进入 WAIT_TARGET，要求调整 ROI 或显式锁定目标；不自动选择最大的人持续累计。

第一版可在 ROI 内只有一名合格候选并持续稳定约 0.5 秒后锁定。目标关联使用上一帧框 IoU、中心位移和尺度比，示例代价：

`cost = w1*(1-IoU) + w2*中心距离/上一框对角线 + w3*abs(log(面积比))`。

先用最大位移和尺度变化做硬约束，再在合格候选中选最低代价。最优和次优过近时判歧义，暂停而不换人。关联参数在训练场移动视频中校准，不能把建议公式当成稳定身份识别。

短暂丢失清除不完整动作但保留计数；超过可关联时间后不自动认定是原训练者。增加 `target_generation`，重新锁定需要确认；没有确认前暂停。持续多人交叉不是首版支持场景。

ROI/持拍手/方向变化使校准失效：暂停、取消未完成动作并要求重新校准。已有会话计数保留并记录配置修订号，界面提示配置变更；不同修订的分类指标评估分别统计。

## 8. 质量门控和归一化

### 8.1 关键点有效性

每点先检查有限性、范围及分数。原型分数阈值可从 0.5 开始，人体检测分数沿用已验证推理配置；分数是模型输出质量指示，不能视为校准概率。核心点为双肩、双髋和持拍侧肘腕；另一侧腕肘为辅助，不要求每帧齐全。

禁止把缺失点填成 `(0,0)`。短暂丢点只在有效样本上计算特征，长缺失不允许插值补成挥拍；关键阶段持拍腕缺失则拒绝本次动作。速度导数不跨越超过最大时间间隔的样本计算。

### 8.2 身体坐标

设肩中点 `S=(LS+RS)/2`，髋中点 `H=(LH+RH)/2`，躯干尺度 `L=|S-H|`。在稳定准备阶段估计尺度，动作内使用其稳健统计值，防止侧身时逐帧缩放制造假速度。

按重力竖直方向建立二维坐标（画面应先校正）：`q_j=(p_j-H)/L`，y 轴向下。特征再根据示范校准对比，不把画面水平轴强行解释成真实身体三维横轴。L 过小或剧烈变化时拒绝；肩宽只作辅助，不作为必须非零的分母。

相对腕位移扣除了髋中心平移，可降低跑动干扰，但髋抖动也会污染腕速，因此需同时检查髋质量。左右手使用同样特征结构，校准文件绑定持拍手，首版不对左右手模板自动镜像复用。

### 8.3 平滑与动态特征

有效点使用按时间间隔计算系数的指数平滑：`alpha=1-exp(-dt/tau)`，tau 可从 0.05～0.10 秒试起。窗口内导数使用有效时间差，速度单位为“躯干长度/秒”。异常跳变先拒绝再平滑，不能把异常点平滑成连续动作。

角度通过点积计算，分母过小则缺失；调用 acos 前钳制浮点结果到 [-1,1]。关键特征建议为：

| 特征组 | 内容 |
|---|---|
| 持拍侧 | 腕/肘的归一化位置、腕速度、肘角。 |
| 双手关系 | 双腕距离、相对轨迹和可见比例；不直接将双手接近判反手。 |
| 躯干 | 肩线方向、髋线方向及其变化；肩线退化时屏蔽相关项。 |
| 动作摘要 | 起止位移、峰值速度、持续时间、前后阶段路径长度比。 |
| 质量 | 每维有效掩码、关键阶段可见性和整体有效比例。 |

## 9. 校准流程与正反手模板

### 9.1 用户流程

1. 确认方向、持拍手和 ROI，锁定训练者。
2. 保持准备姿势约 2 秒，估计静止噪声、人体尺度和腕速基线。
3. 按提示分别做至少 5 次正手和 5 次反手完整挥拍，每次间隔并恢复准备姿态。
4. 候选检测自动切段；用户在回放或采集提示中确认类别，明显错误或遮挡样本剔除。校准动作不进入训练计数。
5. 执行样本内留一比较和两类间距检查；分离不足则提示调整机位/重采，不能强行进入 RUNNING。

每类至少 3 个有效样本才允许建立模板，5 次是采集建议，不是精度保证。校准与测试必须使用不同动作，样本内可分性不能代替独立验收。

### 9.2 时序标准化和距离

完整候选按“动作开始→速度峰值→结束”分为两段，分别重采样到固定长度，例如总共 32 个时间位置；只对小间隔的有效样本插值，大缺口保持掩码。对齐使用腕速峰值，仅代表姿态动作峰值，不能叫击球接触时间。

模板距离使用有效维度加权绝对差或平方差，先按各维校准数据的稳健尺度归一化。每个时间位置必须有足够共同有效维度，整体重合覆盖不足直接 UNKNOWN。对每个类别保留多个示范模板，以最近若干模板距离的中位数作为类距离，降低单个错误模板影响。

设 `d_fh`、`d_bh` 为类距离：

- 最小距离超过校准得出的类内允许范围：UNKNOWN。
- 两类距离间隔 `margin=(d_second-d_best)/(d_second+epsilon)` 低于阈值：UNKNOWN。
- 质量、持续时间和目标连续性均通过时才选择最小距离类别。

阈值先从留一类内距离分位数形成候选，再在独立验证集锁定；数据少时阈值不稳定，需要提示。显示 `MATCH` 或 `MARGIN`，不显示未经校准的“正确概率”。

保存校准格式包含 schema_version、关键点/特征版本、持拍手、方向、模型标识、输入尺寸、机位说明、阈值、模板、质量统计和校准 ID。加载时版本不兼容或方向不一致必须拒绝。文件采用实现时确认的序列化方式；不引入未经评估的 JSON 依赖，首版可用版本化文本格式。

## 10. 动作检测和状态机详细规则

### 10.1 自适应阈值

静止阶段估计腕速中位数 `v0` 和 MAD 噪声尺度，启动/退出阈值分别为 `max(v_min, v0+k*MAD)` 的不同档位，满足启动阈值高于退出阈值，形成滞回。参数 k、v_min 通过数据验证确定；静止校准中出现持续动作则重新采集。

动作检测除了速度，还检查腕部累计位移、引拍趋势和恢复阶段；走路导致的单次速度峰值不应直接提交事件。抬手过头、极短抖动等可作排除规则，但不能声称足以识别全部发球/其他动作。

### 10.2 转换表

| 当前状态 | 条件 | 下一状态 / 行为 |
|---|---|---|
| LOST | 同一目标稳定且核心点合格 | READY，创建新动作上下文。 |
| READY | 校准准备区内稳定后出现有位移的引拍趋势 | PREPARE，分配候选 ID并保存前置上下文。 |
| PREPARE | 持续上升速度及路径变化通过 | SWING，跟踪峰值和轨迹。 |
| PREPARE | 超时、回到静止、质量不足 | 取消候选；稳定则 READY，否则 LOST。 |
| SWING | 峰值后持续降速，随挥位移及最短时间通过 | RECOVER，冻结本次待分类窗口。 |
| SWING | 超时、长缺失、身份/方向变化 | 拒绝候选并 LOST，不计挥拍。 |
| RECOVER | 完整性通过且事件未提交 | 分类并仅提交一次，更新 FH/BH/UNKNOWN。 |
| RECOVER | 回到准备区且短时稳定、间隔满足 | READY，必须有新的引拍才能再次计数。 |
| 任意 | 暂停、ROI变化、重连、时间倒退 | 取消未完成候选，进入暂停或 LOST。 |

RECOVER 可能跨多个帧，但使用 `committed` 标志确保只提交一次。分类窗口的结束时刻为降速/随挥确认时刻；后续等待恢复不能继续改写已提交事件。一个速度脉冲有多个局部峰值时保留同一个候选。

原型范围：动作持续 0.20～1.50 秒、恢复稳定约 0.10～0.20 秒、最长分析间隔约 0.20～0.30 秒。仅作为初始实验值。连续快挥无法恢复准备状态时可能漏计，属于首版需测试并说明的边界；不能简单缩短冷却时间掩盖。

## 11. 配置、命令与生命周期

拟新增命令行：`--tennis-config <path>`。不传则保持普通姿态模式。当前参数数量检查与解析需要一起调整，不能只附加一个分支。

配置分组建议：

| 分组 | 参数 |
|---|---|
| 场景 | enabled、handedness、rotation、calibration_path。 |
| 质量 | keypoint_score_min、min_torso_pixels、min_valid_ratio、max_sample_gap_ms。 |
| 动作 | min/max_duration_ms、ready_stable_ms、recover_stable_ms、阈值倍率。 |
| 分类 | template_length、distance_limit、margin_min、common_feature_ratio_min。 |
| 输出 | show_hud、log_dir、record_pose、preview_rate_limit。 |

解析时拒绝未知键和非法范围，打印有效配置及配置修订号。最大缺失间隔须小于动作最长时间，持续时间下限须小于上限。

控制命令包括 Start、Pause、ResetCounters、BeginCalibration、ConfirmTarget；只在分析线程的帧边界执行。网页线程若新增控制，使用有界命令队列；不能直接写分析状态。纯 HUD 原型阶段可先使用配置和本地校准工具，不必同时扩展所有网页功能。

| 操作 | 计数 | 动作缓存 | 校准 |
|---|---|---|---|
| Pause/Start | 保留 | 清空并重新稳定 | 保留。 |
| ResetCounters | 新会话归零，写明原因 | 清空 | 保留兼容校准。 |
| 相机重连 | 保留 | 清空并重新锁定 | 机位没变时待确认复用。 |
| ROI、持拍手、方向变更 | 保留，标记新修订 | 清空 | 失效并重校准。 |
| 进程重启 | 首版新会话归零 | 清空 | 可加载兼容校准，需用户确认机位。 |

## 12. 预览 HUD 与反馈

HUD 与现有状态/时间区域分开布局，根据图像尺寸计算字号并钳制位置。首版采用 ASCII，避免新增字体依赖：

```text
TENNIS SWING | RIGHT HAND
FH 12  BH 8  UNKNOWN 2  TOTAL 22
RUNNING | TARGET LOCKED | READY
LAST BH | EVENT 22 | MATCH GOOD
ANALYSIS 18 Hz | CALIBRATION A03
```

数字仅为效果示意。暂停和质量不足用醒目状态文字，不清除已有计数。校准时显示 `FH SAMPLE 2/5` 等进度；未知时显示短原因，如 `LOW MARGIN`、`WRIST LOST`。真正取消的候选不显示成新增 UNKNOWN。

网页可用中文解释 FH/BH 和挥拍口径。首版不要求单独的统计轮询接口，画面本身包含计数；后续接口返回同一不可变快照，不能引入第二套统计源。慢客户端只影响预览，不得阻塞状态推进。

## 13. 日志和可回放性

建议每会话生成：版本化会话头、已提交事件 CSV、拒绝候选诊断、可选姿态序列。记录模型标识、配置、时间戳来源、输入尺寸和校准 ID。姿态序列保存原图坐标、分数、目标关联、缺失掩码与单调相对时间；不默认保存原始视频。

CSV 事件字段至少有 session_id、event_id、target_generation、config_revision、start/peak/end_ms、label、quality、distance、margin、reason、fh、bh、unknown。无值用空字段，不能输出 `nan` 假装有效分数。

事件先在内存中提交并更新快照，再异步或有界缓冲写日志；日志失败时在画面和终端提示，不能因重复写入重放计数。首版不承诺异常断电后精确恢复；磁盘恢复和事务一致性另行设计。姿态日志达到容量上限时关闭录制并提示，不能无限增长。

## 14. RK3568 资源和性能验证设计

本方案不增加 NPU 模型，增量主要为 CPU 上的少量关键点计算和模板距离。沿用当前 RKNN 模型输入，不先降低输入尺寸。模板比较为固定长度、小特征维度和少量模板，适合先实现为 CPU 算法；这是结构判断，尚无板端性能结果。

以 30 Hz、2 秒缓存、17×3 个 float 粗估原始关键点约 12 KB/人，另加框、掩码、特征、模板和容器开销。目标关联候选、模板数、缓存长度和日志队列都设置上限；不得用原始全帧视频作为默认时序缓存。

测量采集、预处理、推理、后处理、特征、模板分类、HUD、编码、发布各阶段 p50/p95；记录实际分析采样间隔和长缺口。目标可暂定分析 ≥15 Hz、预览 ≥10 fps、动作完成后 1 秒内显示新计数，均须实测确认。分析频率低时提示 `LOW RATE` 并暂停不可靠候选，不能为了保持画面流畅而假定时序质量足够。

30 分钟运行观察温度、降频、内存、计数稳定性；分别比较普通姿态预览与启用分析的增量。先优化 JPEG 分辨率/发布频率和无用复制，再判断是否需要多线程。若必须并行，只保留有界最新帧队列并传播时间戳，不能无界积压。

这里的可行性依据是现有本地 RKNN 姿态路径和算法规模，不构成准确率或实时性承诺。Tennis-Vision 的 MediaPipe 深度规则和桌面端指标不能直接作为板端验收依据。

## 15. 测试矩阵和验收

### 15.1 核心测试

| 场景 | 预期 |
|---|---|
| 同一完整动作重复输入/绘制 | 相同序列号或事件不重复计数。 |
| READY中摆手、走路、抖腕 | 不应仅因腕速峰值直接计数。 |
| 正手随挥跨身、双手反手 | 使用完整窗口模板，不能被单帧跨中线规则主导。 |
| 腕点 NaN/Inf、零尺度、时间倒退 | 拒绝输入，不崩溃、不产生事件。 |
| 短丢点、长丢失、身份歧义 | 按质量策略取消候选，保留已提交计数。 |
| ROI变化、Pause、Reset、重连 | 严格遵循生命周期表，不产生半个动作计数。 |
| 多个速度峰值与快速连续挥拍 | 一动作不重复，相邻动作漏计率单列。 |
| 多客户端、慢网络 | 计数与单客户端相同。 |
| 无模板/模板不兼容/类间不可分 | 不启动分类，提示校准原因。 |
| 仅少量样本得到高匹配分数 | 不把分数当成准确率，独立数据仍需评估。 |

### 15.2 数据与指标

人工标注动作边界、FH/BH、可判定性、遮挡和负样本。独立测试动作不能参与模板建立；分别进行“同人新动作”和“新参与者重新校准后的测试”，不能声称少样本个性化模板具有免校准跨人泛化能力。

报告事件一对一匹配的 precision/recall/F1、FH/BH 宏平均 F1、每类计数绝对误差/相对误差、UNKNOWN 占比、分类覆盖率及负样本误触发。事件峰值仅作统一时间锚点，匹配容差在评估前固定，例如 ±0.25 秒作为起点；动作标注和预测使用同一锚点定义。

拟议受控验收目标：FH/BH 宏平均 F1 ≥0.90、每类计数误差 ≤5%、可分类覆盖率 ≥85%、负样本误触发 ≤1 次/10 分钟。真值为零的类别仅报告误报绝对数。UNKNOWN作为分类弃权纳入端到端漏分类评估，不能只在成功分类样本上计算高分。目标尚未达到，需数据量和测试人员覆盖共同支持。

## 16. 实施拆分与是否编码的决策

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| P0 拍摄和数据验证 | 原始姿态质量报告、正反手及负样本片段 | 腕/肘/躯干关键点可用，实际采样频率满足动作分析。 |
| P1 离线基线 | 回放工具、归一化与模板算法、校准规则、事件评估 | 独立动作可区分，误触发可控；不可分则调整机位或比较模型。 |
| P2 板端最小闭环 | 单人关联、状态机、FH/BH/UNKNOWN HUD与事件日志 | 回放与现场结果一致，重复计数和生命周期测试通过。 |
| P3 使用体验 | 网页校准/暂停/重置、配置保存与状态反馈 | 不影响计数一致性与性能。 |
| P4 验收 | 独立精度报告、30分钟性能报告及已知限制 | 满足约定指标，或明确缩小适用范围。 |

建议下一步先进行 P0/P1 验证，再决定是否正式实现 P2。若用户希望先看预览效果，也应将最小闭环标为实验功能，不将演示计数宣称为已验收识别效果。
